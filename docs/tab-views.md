# tab-views

**Does** — `ZenshapeWindow`: one `BaseWindow` holding our strip view on top and one `WebContentsView` per Onshape tab underneath. Owns layout, the navigation policy per tab, `window.open` → tab adoption, the sign-in tab, drag reordering, split view, page locks, and hiding the tab bar to a top gutter.

**Why it exists** — Tabs need several pages in one window, which `BrowserWindow` can't do. Keeping it out of `main.ts` keeps the app lifecycle separate from per-window state.

**Talks to** — `tabs.ts` (the list model), `web-preferences.ts`, `navigation.ts`, `strip-api.ts` (IPC to the strip). `main.ts` creates it and persists `snapshot()`.

**Gotchas**

- Onshape views are added at index 0 so the strip is always on top. Only the active view is visible.
- **Hidden tab bar** (`stripHidden` = Hide Tab Bar, or zen on with Hide Tab Bar in Zen Mode): pages start below the gutter (12px on macOS, 24px in macOS full screen so there's room to stop before the screen's top edge, where macOS brings down its own bar; see Window controls off macOS); the strip view shrinks to that gutter and the window buttons go or shrink into it (see below). Hovering it `peek`s: the view goes back to 36px over the page (pages don't move) and the strip slides down; `unpeek` slides it up, then shrinks the view 250ms later. Resizing the strip view (and native menus) fire pointer-leaves the user didn't make, so `unpeek` checks the real cursor (`cursorOverStrip`) and, if it's still over the strip, re-checks every 250ms until it leaves. UI tests replace `cursorOverStrip` to stay independent of the real mouse. The gutter is our view, not space inside Onshape's page, so it works on every page with no CSS in Onshape; it can't be a window-drag region, since drag regions get no hover on macOS. Peek overlays the page rather than pushing it down, so Onshape's 3D view doesn't re-lay out on every hover. Zen doesn't rewrite the Hide Tab Bar setting, so turning zen off restores it.
- **Window buttons** go through `showWindowButtons`, which does nothing in full screen. There macOS draws them in its own slide-down bar, and calling `setWindowButtonVisibility` on every peek (even with `true`) knocked them out of it, while a single call on entering is fine, which left no way out of full screen. So entering full screen turns them on once, and leaving reapplies the hidden-tab-bar rule (the `WORKAROUND:` comment in `tab-views.ts`). Off macOS full screen just reapplies that rule (Windows and Linux draw no controls in full screen), so the overlay keeps the gutter's height and color. All of it goes through `setWindowButtons`, the one place each platform's call lives: macOS's `setWindowButtonVisibility`, or `setTitleBarOverlay` elsewhere. Each exists only on its own platforms; `setWindowButtonVisibility` off macOS threw inside the constructor, before the first layout.
- **Window controls off macOS:** `windowControls()` gives Windows and Linux Electron's `titleBarOverlay` (their own minimize, maximize and close at the strip's right end, `#1c1c1c` with white symbols, 36px tall) and macOS its traffic-light position instead. The overlay can't be hidden, only resized and recolored, so a hidden tab bar's gutter holds it: `setWindowButtons` sets the overlay's height and its color to the gutter's (`GUTTER_COLORS`: `#1c1c1c` bar, `#333333` zen, white drawing with `#1c1c1c` symbols), and a peek puts it back to 36px and `#1c1c1c`. `push` re-applies it when the gutter's color changes while hidden. `gutterHeight` is the one source of the gutter's height: the page layout and the strip view use it, and strip state carries it (with `gutterColor`) to the strip's CSS. macOS: 12px. Linux: 26px (`LINUX_GUTTER`); its buttons are never under 20px and are centered, so 26px leaves 1px above and below (at 12px they hung onto the page; at 20px they touched both edges). Windows won't draw its buttons below its caption height (Electron's `WinFrameView::TitlebarHeight`), so the hidden overlay is set to 0, Windows' own minimum, which Electron then reports as the real height (`LayoutWindowControlsOverlay`). Electron sends the overlay's area to every `WebContentsView`, clipped to it; the strip sends it back (`controls-height`), and `controlsMeasured` takes it, rounded up (it can be fractional, and `setBounds` takes only integers), as the gutter while hidden and unpeeked. Until then the gutter is 36px, so the strip view is tall enough to see the whole height; once it's as short as the buttons it can't see them grow, so maximize, unmaximize and display changes start the measurement over (`remeasureControls`). Seen on the CI runner: 31px (buttons 30px tall from y=1). The strip pads its right by what `env(titlebar-area-x/width)` leaves of the width.
- `showStripMenu` (right-click on empty strip space or the Z): Hide Tab Bar, Zen Mode, Hide Tab Bar in Zen Mode (checkboxes, `stripOwnItems`); off macOS, then the app menu as submenus (`opts.appMenu()` through `stripMenuTemplate`, `app-menu.ts`), rebuilt per popup. The popup's callback can run after the window closed (Quit from that menu); `unpeek`'s `closed` check covers it. With `ZENSHAPE_TRACE_MENUS=1` (set by the smoke test's launch scripts) the Z's menu prints `strip menu: opened: <labels>` and `strip menu: closed after <n> ms` on stdout, since UI Automation can't be relied on to read it.
- `window.open` uses `createWindow` and adopts Electron's `options.webContents`, so `window.opener` keeps working. The adopted view takes `onshapeWebPreferences()` only, never Electron's passed-in prefs.
- Restored tabs create no view until selected: each Onshape document is a heavy WebGL app.
- **Drag to split:** dropping a strip tab onto another tab → `splitOnto`; dragging it below the strip → `drag-page` (previews via the overlay view) and `drop-page` → `dropOnPage`. `planDrop` decides: with a split on screen, an outside tab replaces the pane under the pointer, and a split tab moves to the nearest edge; otherwise the dropped tab splits with the active one. Moving a split tab back between strip tabs unsplits it.
- **Splash view:** our page in `#splash` mode, the topmost view, covering the whole window. `showSplash('launch')` (from `main.ts` at startup) hides itself after 2.5s; `showSplash('about')` (App menu → About Zenshape) stays until dismissed. A click or Esc sends `dismiss-splash` (only accepted from the splash view); `hideSplash` pushes `splash: null` so the page fades, then hides the view 300ms later.
- **Update notice:** `setUpdate` stores a newer release (from `main.ts`) and pushes it as strip state; the strip's button sends `open-update`, which opens its release page in the browser.
- **Overlay view:** our page in `#overlay` mode, shown over the page area only while dragging; it never takes input, since the strip view keeps the pointer while the button is held.
- **Split view:** `split` pairs two tabs. When the active tab is one of them, both are laid out with `splitLayout` and the divider view sits between them. The active tab follows page focus (`focus` event). Closing either tab or Unsplit ends it; it isn't saved.
- **Back/forward:** `goBack`/`goForward` act on the active tab (strip buttons, ⌘[ ⌘], mouse buttons over the strip) or, for mouse buttons over a page, on that page. Mouse back/forward come from `input-event` mouseUp with `button: 'back' | 'forward'`; that's macOS's only route (Electron's `app-command` is Windows/Linux) and the values are missing from Electron's typings. `canGoBack`/`canGoForward` ride along in strip state.
- **Copy Link** in the tab menu copies the tab's saved URL (works for unloaded tabs too).
- **Gutter color** (`gutter()` → `state.gutter`): `bar` unless zen is on over a document; then `drawing` if one of the tab's frames is that element's drawing (`isDrawingFrameFor`), else `zen`. Read from frame URLs, no script in the page; `did-frame-navigate` re-pushes because the drawing's frame loads after the page. In a split the gutter follows the focused pane.
- **Zen mode:** `setZen` inserts/removes `zen.ts` sheets on every page with a fade, then nudges bounds so the canvas re-fits. New documents get the sheets on `dom-ready`.
- **Divider:** our page in `#divider` mode in its own view (the 36px strip view can't take the pointer over the pages), above the pages and below the strip. On `divider-start` it's stretched over the whole page area so the pointer can't leave it; `divider-move` sends the ratio; `divider-end` shrinks it back. Only the divider may send `divider-*` commands.
- **Locks:** `lockedUrl` + `inLockScope`. A full load out of scope is stopped in `will-navigate` and opened in a new tab. An in-page (pushState) change out of scope can't be stopped, so the tab reloads `tab.url` (never updated out of scope) and the destination opens beside it. `goBack()` was tried and fought Onshape's router, leaving the wrong folder and duplicate tabs. Duplicate reports of one change within 2s open one tab. Sign-in pages are exempt.
- **Sign-in loop breaker:** a tab returned from the sign-in tab that hits sign-in again within 10s is held (an auto-continuing sign-in hop, not a real logout). If it's still on a sign-in page 2s later (`SIGN_IN_SETTLE_MS`) and has stopped loading (a slow hop is judged once `did-stop-loading` fires), it's diverted after all: a real sign-out soon after signing in otherwise got no sign-in tab, so no fill.
- **Sign-in tab:** when any tab lands on a sign-in page, its page moves into a temporary "Sign in" tab at the far left and the tab itself goes back to unloaded, keeping its URL and title. Signing in closes that tab and loads the one you were on; with nothing to go back to, it just becomes a normal tab. It's never pinned or saved.
- **Watching the sign-in page:** while the sign-in tab shows Onshape's sign-in page, its view has `webContents.debugger` attached (`watchSignInPage`, run from `changed()`; the `Debugger` is captured at attach, since a destroyed contents' `debugger` can't be read). It detaches when that page or tab goes (including a redirect off Onshape, such as an SSO provider after Continue, which `will-navigate` doesn't see), reattaches if the tab comes back to the sign-in page, and no other view ever has it. Every fill rechecks the URL around each await, so a redirect mid-fill types nothing.
- **Which page a sign-in opens on** (`zenshapePageFirst`, one place so the choice is easy to change): with nothing saved, Zenshape's page; with a login saved, Onshape's own page, filled as below.
- **The saved-login path:** while the sign-in page is watched, `autofillTick` reads its focus every 250 ms (paused while Zenshape's page shows or a run is busy, so nothing is typed behind the page) and, as Onshape's empty email or password field takes focus, has the fill routine type it (`docs/sign-in-fill.md`: every guard, the account check included, lives there). No key is pressed on this path: Continue and Return are the user's. Each key (`before-input-event`, which Electron fires synchronously even for the run's own keys) or press (any `input-event` but moves, wheels and keys: a click, a tap, a touch) goes to the routine's `pressed` and takes a new reading.
- **Zenshape's page:** with nothing saved, a new sign-in tab shows the splash view's Saved Sign-in page (`splash: 'saved-sign-in'`) over Onshape's; Saved Sign-in… opens it any time. State carries `savedSignIn: { email } | null`: only the email is decrypted, for that page (`showSavedEmail`); the password never leaves main. Its one button sends `sign-in` (only the splash view may, only while that page shows) with the email and the typed password, or null to keep the saved one. `signInFromPage` saves only if nothing was saved, the email changed or a password was typed, so an unchanged Sign in calls nothing in `safeStorage`; then it runs `sign-in-sequence.ts` on the watched page: email, Return (Onshape's Continue), password, Return, typed with `insertText` and keys sent with `sendInputEvent` (`pressReturn`), no script. Seen 2026-11-19: Onshape focuses its password field by itself, 158 ms after Continue. While it runs (`runSignIn`), Zenshape's page stays in front and `signInRun` ticks off each step (save, email and Continue, password and Return, signed in). The run first gives the covered sign-in page focus (`contents.focus()`): the splash view holds it after the click, and Chromium matches `:focus` only in the focused view, so without it every focus read saw no field and the run timed out (seen in a test build; confirmed in a scratch Electron 45 run). Covered, the page keeps loading and takes focus and typing. If the user switches to another app mid-run, the focus reads see no field and the run times out at that step. One press at a time: `signInBusy` holds from the press (the list shows from then, the save pending, since it may wait on the keychain) until the run's list leaves the screen; `runSignIn` always reaches `endRun`, even on an error; the reads and their timeouts are the fill routine's (`docs/sign-in-fill.md`). Esc does nothing mid-run: the covered page has focus. Signed in (`finishSignIn` completed that tab, `signedInTab`; a tab the user closed mid-run isn't; `finishSignIn` also hides Zenshape's page when no run is busy, so it never stays over a signed-in document): the check shows for 600 ms, then the signed-in page. Handed over (Onshape took the password and focused a field of its own next step, a code): it ends the same way, every step green for 600 ms, then Onshape's page comes forward for the code: the password was accepted, so it looks like a sign-in, not a stop. Stopped (a field with text, a timeout, the password asked again, a page off the sign-in URL that isn't signed in): the step list marks where and why for 2.5 s, then Onshape's page comes forward (`endRun`); Saved Sign-in… reopened in that moment cancels it. After a stop, the rest is the user's: the autofill fills a field as it takes focus, and they press Return. Esc (`dismiss-splash`) shows Onshape's own page.
- **A page can close its own tab** (`window.close()`, or the page that opened it calling `w.close()`). Electron then destroys its contents, and `view.webContents` reads `undefined` from then on, already inside `'destroyed'`, though the typings say it can't. So `addView` keeps the contents it was created with, and on its `'destroyed'` drops the zen sheets by that contents and, if the view is still in `views`, closes its tab as Close Tab does (`pageClosed`), finding the tab by the view. Zenshape's own closes (Close Tab, the sign-in moves, the window's teardown) drop the view from `views` in the same step as `close()`, and `'destroyed'` comes later, so this only acts on a close the page started. An adopted popup's tab remembers its opener (`openers`): if the popup was the active tab, its close lands back on the opener while it's open, otherwise where Close Tab would. The last tab closing itself closes the window, as ⌘W does. Before this, the dead view stayed in `views`, and every push threw "Cannot read properties of undefined (reading 'isLoading')".
- **Window teardown** (`dispose`, on `'closed'`): Electron 45 destroys the window before `'closed'`, and each page dies about 60 ms after its `close()`, still loading and sending events until then. So `dispose` sets `closed` and empties `views` first, then closes the pages; `push`, `layout`, `changed`, `pageClosed`, the window-open handler (deny), `will-navigate` (stops it, opens nothing) and the peek and remeasure timers all ask `closed`, never the window or the strip (the strip outlives the window). Before this, a loading event in that gap reached `push` → `isFullScreen()` and showed "Object has been destroyed" on every close on Windows.
- Handlers look up their tab by `webContents` each time, because a view can move from a tab to the sign-in tab.
- Titles only come from `page-title-updated` with `explicitSet`, and placeholders (blank, "Onshape", "Sign in") are ignored, so a pin can't be renamed by a page that's still loading or redirecting.
- Right-click → Rename… focuses the strip and pushes `renamingId`; the strip edits in place and sends back `rename` (null = cancelled). Focus returns to the active page afterwards. Disabled while collapsed.
- Pins show their name like any tab, minus the close button. Page captures and title abbreviations were both tried and dropped.
- The strip view may reload its own page (Vite's dev reload) but navigate nowhere else.
- IPC is accepted only from the view that owns the command (strip, divider, or splash), and commands are shape-checked.
