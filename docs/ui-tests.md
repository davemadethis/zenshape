# ui-tests

**Does** — `npm run test:ui` (`test/ui/`, `vitest.ui.config.mts`) builds the app, launches it against live Onshape with a throwaway profile and checks the layout rules for the strip, tabs, split, locks and zen mode. `npm run ui:probe` checks every `onshape-dom.ts` landmark on a document and a list page and, for any that miss, prints candidate elements found by text or position.

**Why it exists** — Onshape can change its front end at any time. A failure names the landmark that moved, and the probe shows where it went, so the fix is one edit in `src/onshape-dom.ts`.

**Talks to** — `ui-targets.local.json`, the built app over Chrome DevTools Protocol (`cdp.ts`, Node's built-in WebSocket; no Playwright) and the Node inspector (`ZENSHAPE_E2E=1` exposes the window object to it). `harness.ts` (`Ui`), `global-setup.ts`, `targets.ts`.

**Gotchas**
- Not in the project's check script, quick or full: it needs network and a login, and takes minutes. It runs at release, or on request.
- **Login:** `global-setup.ts` copies the cookies from the `Zenshape Dev` profile (`npm start`) into the throwaway profile, so your own tabs and settings are never touched. If Onshape asks to sign in, it closes its one window and fails with "Sign in once via `npm start`". Then sign in once in `npm start` and quit it. Don't loop on reruns.
- **Runs the built app** (`.vite/`) via `electron .` on free ports, so it can run beside your own `npm start`. `ZS_SKIP_BUILD=1` skips the build, but a stale dev bundle (one pointing at Vite's dev server) then fails to load.
- **Targets** are pages in your own Onshape account, read from `ui-targets.local.json` at the repo's root: a JSON object with `owned` (your documents list, `…/documents?resourceType=resourceuserowner&nodeId=<id>`), `otherFolder` (a folder's list page), `document` (a Part Studio, `…/documents/<did>/w/<wid>/e/<eid>`), `drawing` (a drawing in that document) and `team` (a Teams page, or empty to skip that check). `ZS_TEST_OWNED`, `ZS_TEST_FOLDER`, `ZS_TEST_DOC`, `ZS_TEST_DRAWING` and `ZS_TEST_TEAM` override each one. Without the file or the variable, the suite stops and prints the file's shape.
- Tests assert geometry and computed styles (positions, sizes, opacity, display) and the odd pixel, never pixel diffs: Onshape renders live data. Each saves a screenshot to `test-results/ui/` for a human look.
- Native menus can't be clicked, so tests call the window's methods (`ui.win(...)`).
- **Covered windows keep rendering:** with `ZENSHAPE_E2E=1`, `main.ts` adds Chromium switches against backgrounding, and the harness finds the active page by the active tab's URL, not `visibilityState`. Without both, results depended on what covered the window. Tests also wait for the launch splash to go.
- Optional landmarks (billing banner, welcome/last-opened panes, detail-pane divider, `docForeignFrame`) are checked as "not visible if present"; the probe marks them – instead of ✗.
- `vitest.config.mts` keeps unit runs off `test/ui`. Use `--silent=false` to see `console.log` from a UI test.

## Smoke (CI)

**Does** — `.github/workflows/smoke.yml` first runs `npm test` (the unit tests) on each runner, after `npm ci` and Electron's download (`node node_modules/electron/install.js`); then it builds the installers the release ships (Windows `Zenshape-Setup.exe`, Linux `.deb`), installs each on a fresh runner (`windows-latest`, `ubuntu-22.04`), starts the installed app signed out with `--remote-debugging-port` twice (as installed; then on a fresh profile seeded with `{"stripCollapsed":true}`, i.e. the tab bar hidden), and each time runs `npm run test:smoke` (`test/smoke/`, `vitest.smoke.config.mts`) against it over CDP. It checks: (a) an Onshape page and the strip appear within 60 s; (b) the Onshape page is its sign-in page (anything else, such as a bot challenge, fails with the URL); (c) the strip shows the "Sign in" tab; (d) layout geometry: the strip is 36 px tall, the page has the strip's width, and the two stack within the window (`Page.getLayoutMetrics`; no script runs in Onshape's page); (f, Windows and Linux) the strip sees the window controls overlay (`navigator.windowControlsOverlay`), the Z ends left of it, its area fills the strip view's height (36px; when hidden, the gutter: 26px on Linux, Windows' own caption height, 12–36px), and there's no 86px inset; (g, hidden launch) peeking via the strip's bridge brings the strip and the overlay back to 36px, and leaves it peeked; (e) the app's output has no `TypeError`, `is not a function`, `Uncaught` or `UnhandledPromiseRejection`. Outside the test, the workflow fails if any top-level window is Electron's main-process error box ("A JavaScript error occurred in the main process"; on the runners it's a dialog the app owns captioned "Error"), looked for 15 s after launch and again after the test (`test/smoke/no-error-dialog.{sh,ps1}`; window lists in `windows.txt`). Each launch is `test/smoke/launch-{windows.ps1,linux.sh}`; the hidden one sets `ZS_SMOKE_HIDDEN=1` and writes to `smoke-out/hidden/`. On Windows, UI Automation lists the Minimize/Maximize/Close buttons with their rectangles (`controls.txt`); the first launch fails without them, and the hidden one fails if they reach below the gutter, or if it finds none to check (the test writes the strip's hidden height to `gutter.txt`). Crashes are caught by e (async throws, which print an unhandled rejection) and the error-box check (synchronous throws, which print nothing). d checks geometry only: it doesn't catch a crash, since a constructor that throws after the views exist still leaves them laid out (seen when its guard was reverted).

**Run it** — `gh workflow run smoke.yml --ref master` (once the workflow is on master), or push any commit to a `smoke/<name>` branch: `git push origin HEAD:smoke/<name>`, and delete the branch after. Nothing else triggers it. Each run uploads `smoke-windows` and `smoke-linux`: CDP screenshots of the strip and the Onshape page, a whole-screen shot (window frame and controls, or their absence), and under `hidden/` the same for the second launch plus `screen.png` taken before its test (hidden) and `screen-peeked.png` after, `targets.json` and the app's output. Look at the screenshots; the test doesn't judge them.

**Unit tests first** — `npm test` runs `vitest.config.mts`'s files: `test/**/*.test.ts` and `scripts/**/*.test.ts`, without `test/ui/` and `test/smoke/`. A failure stops that OS's job before the build, and launch 2 runs only once the app is installed. It is the only Windows run of the unit tests before a tag: the release runs them too, but only on the public repo.

**Can't check** — anything behind sign-in (documents, zen, splits, locks): CI has no Onshape login, by choice. Nor macOS (the Mac UI suite covers it) or the `.rpm`.

**Cost** — about 4 minutes per OS per run, mostly the build, plus the unit tests. Windows minutes bill at 2×, so a run costs roughly 9 Linux-minutes. Hence on demand only.

**Gotchas**
- Build with every maker (`electron-forge make`), never `--targets`: that builds a fresh maker without our options, so the `.deb` looks for a lowercase binary and Setup.exe gets a different name.
- Windows: Squirrel's `Setup.exe --silent` starts the app once after installing. The workflow stops it (and logs what it stopped), waits until no Zenshape process is left (single-instance lock), and deletes the profile that first run wrote to `%APPDATA%\Zenshape`, so the test's launch starts fresh. Packaged builds ignore `ZENSHAPE_USER_DATA`. The runner ends a step's processes when the step finishes, so starting the app, the test and the screen grab share one step. stdout and stderr go to `app.log` and `app.err.log` (`ZS_SMOKE_LOG` takes both, `;`-separated).
- On Windows, `path.join` joins with `\`. A test fake keyed by exact path (the saved sign-in in `test/web-preferences.test.ts` and `test/sign-in-probes.test.ts`) only matches a seed built with `path.join`, as the app builds it; one spelled with `/` passes on the Mac and fails there.
- Linux: Xvfb plus openbox, so a decorated window would show its decorations. dbus errors in `app.log` are the runner's, not ours.
- Linux profile: packaged builds keep it in `~/.config/Zenshape` (productName), where the hidden launch seeds `app-state.json`.
- Locally: `ZS_SMOKE_PORT=<port> ZS_SMOKE_LOG=<log> npm run test:smoke` against any running Zenshape started with `--remote-debugging-port=<port>` and no login (a dev run: `ZENSHAPE_USER_DATA=$(mktemp -d) npx electron . --remote-debugging-port=<port>`).
