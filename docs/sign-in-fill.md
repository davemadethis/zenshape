# sign-in-fill

**Does** — `fillField`: the one routine that types a saved login into Onshape's sign-in page, and `pressReturn`, the one that presses a key on it; every guard lives here.

**Why it exists** — Every fill bug found so far was one fill path missing a guard another path had. With one door, a guard can't be on one path and not another. A test reads `src/` and finds `.insertText(` and `.sendInputEvent(` only in this file.

**Talks to** — `tab-views.ts` (gives it the watched page as a `FillPage` and its per-page `FillState`; the autofill calls it with trigger `focus`), `sign-in-sequence.ts` (the Sign in run, trigger `run`), `sign-in-focus.ts` (the focus read and the account reading), `saved-sign-in.ts` (the decrypt), `sign-in-log.ts`.

**Gotchas**
- Checks, in order: one fill at a time on the page (`busy`, which the run treats as "not yet"); still the watched page, the sign-in tab active, on Onshape's sign-in URL (`left`); a login saved; once per page for `focus` (the run may fill again: you asked); focus moved only for `run`; an empty focused field of the asked kind; for the password, the account; the decrypt; then, right before `insertText`, the account again, the focused field again (the last read, since typing goes wherever focus is), the page, and no key or press since the fill began (`presses`: a Shift+Tab or a click into the email input mid-fill stops it).
- **The account:** a live reading of every email input on the page decides when there's one with text (`readAccount`; Onshape's password step keeps one, seen 2026-11-20). Otherwise the last verdict, taken by the autofill's tick and at each key or press. A key or press clears it only when, as of the last reading, the page has an email input (`pressed`): it may have changed the email or continued with it; on a step with none it can't have, and the verdict stands. A reading begun before a clearing press doesn't count (`clears`), so a select-all, paste and Return can't ride on an old sample. `other` at the password step leaves the password to the user on that page for good; another email seen earlier only sets the verdict, so a stray edit put right doesn't block it. No verdict types nothing. The saved email is decrypted once per saved login (`SavedSignIn` keeps it, and drops it on save and forget); a save or forget also bumps `version`, and a page's verdict and "for good" from the old login are dropped (`syncLogin`), at the start of each fill and reading and whenever a reading straddles a change. A fill whose login changed while it ran types nothing: it checks `version` right before `insertText`. A reading that fails counts as "may have email inputs", so a press still clears. The log's `account` line (which source decided, and the verdict, never an email) is written once per change.
- `pressReturn` sends Return as keyDown, char and keyUp; only the run calls it, right after a fill typed. Electron fires `before-input-event` for the keyDown synchronously (seen in a scratch Electron 45 run), so tab-views' key handler starts the account reading the run's password relies on as the key goes out. Its answers come after the page has the key; Onshape's password step keeps the email input, so it still reads the email continued with. The autofill path presses nothing.
- The page's protocol calls go through `sign-in-focus`'s allowlist (`guard`): DOM and Accessibility only, so nothing types through the debugger either.
- Each focus or account read gives up after 2 s, so a protocol call that never answers can't hang a fill.
- No click fill and no File menu fill: both were removed.
- **The run's email step with text already there:** if Onshape's email field holds the saved email (the account reading says `same`), the step is done with nothing typed (`already`), so a Sign in after the email was typed behind Zenshape's page ticks on. Another email there is left alone and stops the run. The autofill never counts text as done.
